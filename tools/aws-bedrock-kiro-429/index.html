AWS Bedrock / Kiro 配额与 429 完全指南

配额页面怎么看 · TBD 动态配额 · Kiro 限流 · "256V 账号"误区 · 429 排查实战

全部内容，六句话

1
AWS 给每个账号设了调用上限（每分钟请求数 RPM、每分钟 token 数 TPM）。两个控制台页面——Service Quotas 和 Bedrock 的 Model quotas——都是看这些上限的，前者全量平铺，后者按模型整理。
2
真正限制你的是 "Applied value"，不是 "AWS default"。默认值只是纸面数字，AWS 会按账号信任度动态调低——新账号 applied 值可能只有默认值的零头，甚至是 0（模型退役/被禁用）。
3
TBD = 动态配额：AWS 不公布固定值，按区域容量和账号历史用量浮动分配。不能自助提额，只能靠稳定用量慢慢涨，或走工单。
4
配额是"上限"不是"保证"。区域容量紧张时（us-east-1 / us-west-2 高峰很常见），远没到配额也会 429。同一模型走不同路径（直连 / 跨区域 profile / mantle 端点）吃的是不同的配额。
5
Kiro 的 429 和你的 AWS 配额无关。Kiro 是托管服务，推理跑在 AWS 自己的容量池上，限流由订阅套餐、短窗口频率、风控（VPN/代理会触发）和高峰容量决定，阈值不公开、不可自助调。
6
"256V 账号"和 Bedrock 配额没有关系。256v 是 EC2 的 vCPU 配额，AWS 各服务配额相互独立。高配 EC2 账号的 Bedrock applied 值照样可能被压得很低——唯一可靠的做法是用 CLI 查自己账号的真实数字（见 ⑦）。

429 了？30 秒定位

哪里报的 429？ ├─ Kiro IDE ──────────────→ 看标签页 ⑥（和你的 AWS 配额无关） └─ 自己代码调 Bedrock │ ├─ 报错含 "Too many requests" → RPM 被打满 ├─ 报错含 "Too many tokens" → TPM 被打满（先怀疑 Output TPM） │ ├─ 第一步：确认调用路径（三者配额独立） │ anthropic.claude-* → 直连按需配额 │ us.anthropic.claude-* → Cross-region 配额 │ BedrockMantle 客户端 → [bedrock-mantle endpoint] 配额 │ ├─ 第二步：查自己账号的 Applied 值（标签页 ⑦ 的 CLI） │ Applied 远低于 Default → 账号被动态降额（新号常见） │ 查不到 / TBD → 动态配额，看标签页 ④ │ └─ 第三步：Applied 明明够却间歇性 429 → 区域容量拥挤，错峰 / 换区 / 走跨区域 profile

三个对象的对照表

Bedrock（自己账号调用） Kiro IDE
限额能查到吗 ✅ Service Quotas / Model quotas 页面、CLI（TBD 模型除外） ❌ 不公开精确阈值
能提额吗 ✅ 可调配额自助申请；TBD 靠用量增长/工单 ❌ 只能升级套餐、调整使用节奏
429 主因 账号被动态降额、Output TPM 打满、区域容量拥挤 短窗口频率、风控（VPN/代理）、高峰容量、套餐额度
和 256v 有关吗 ❌ 无关（vCPU 是 EC2 的配额） ❌ 完全无关（不走你的 AWS 账号）

两个配额页面的关系

AWS 对每个账号调用 Bedrock 设了上限，这两个页面都是看上限的，入口和组织方式不同：

对比项 Service Quotas 控制台 Bedrock 控制台 → Model quotas
入口 Service Quotas 服务（AWS 通用配额中心）→ 选 Bedrock Bedrock 控制台左侧菜单里的 Model quotas
组织方式 一条条配额平铺，靠搜索框过滤（如搜 "opus"） 按模型组织，直接看每个模型的推理配额
覆盖范围 Bedrock 的全部配额：推理、批量、微调、Agents、Knowledge Bases…… 聚焦模型推理配额（RPM / TPM）
特有内容 Applied vs Default 对比、Adjustability（是否可调） 能看到 TBD（动态配额）模型的状态
提额入口 ✅ Request increase at account level ✅ 也有申请入口（部分转 Service Quotas 或工单）
┌──────────────────────────────────────────────────┐ │ AWS 账号的 Bedrock 配额（按区域） │ └──────────────────────────────────────────────────┘ ▲ ▲ │ 全量视角（所有配额类型） │ 模型视角（推理配额） │ │ ┌───────────────────┐ ┌────────────────────────┐ │ Service Quotas │ │ Bedrock 控制台 │ │ → Bedrock │ │ → Model quotas │ └───────────────────┘ └────────────────────────┘

底层是同一套账号配额，Model quotas 是 Bedrock 给自己做的"专属仪表盘"。

什么时候看哪个

  • 查某个模型的推理限额 / 看到 TBD → Model quotas（标签页 ③④）
  • 查批量推理、微调、Agents 等非推理配额 → Service Quotas（标签页 ②）
  • 审计账号：哪些提额过、哪些被清零 → Service Quotas（有 Applied vs Default 对比）
  • 程序报 429 → 按标签页 ⑤ 的流程走
配额是按区域（region）独立的。us-east-1 和 us-west-2 是两套完全独立的数字，要用控制台右上角的区域选择器分别看。

Service Quotas → Bedrock 配额列表

https://<region>.console.aws.amazon.com/servicequotas/home/services/bedrock/quotas

AWS 通用的"配额总账本"，列出你的账号在当前区域对 Bedrock 的所有限额。用顶部搜索框过滤（比如搜 opus、tokens per minute）。

每一列怎么读

列名含义
Quota name 配额名，一般是「维度 + 模型」，如 Output tokens per minute for Claude Opus 4.8
Applied account-level quota value ⭐ 你账号实际生效的值——真正限制你的是这个数字
AWS default quota value 纸面默认值。
Applied > Default → 提额成功过；
Applied < Default → 账号被动态降额（新号常见）；
Applied = 0 → 该配额对你被禁用（如已退役的 Claude 3 Opus）
Utilization 当前用量占比。大部分推理配额显示 Not available（不上报），实际用量要看 CloudWatch 或自己统计
Adjustability Account level = 可申请提额；Not adjustable = 硬上限，申请也没用

Bedrock 配额的常见类别（搜索关键词）

关键词是什么
requests per minute（RPM）每分钟调用次数上限
tokens per minute（TPM）每分钟 token 量上限——通常先打满的是 Output TPM（一般比 Input 小 5~10 倍）
Cross-region model inference走跨区域推理 profile（模型 ID 形如 us.anthropic.*）的独立配额
[bedrock-mantle endpoint]走新 Messages-API 端点（SDK 的 AnthropicBedrockMantle 客户端）的独立配额
Batch inference批量推理：文件大小、任务大小、并发数（多为固定值不可调）
其他微调任务数、Provisioned Throughput、Agents / Knowledge Bases 等
同一个模型走不同调用路径，吃的是不同的配额。排查限流前先确认代码用的是哪条路径。

提额操作步骤

  1. 搜索并勾选目标配额（必须是 Account level 可调的）
  2. 点右上角 Request increase at account level
  3. 填入期望值 → 提交
  4. 小幅提升通常自动批；大幅提升转人工审核（可能要说明用量场景），预留几天
  5. 在左侧 Quota request history 跟踪审批状态

Bedrock 控制台 → Model quotas

https://<region>.console.aws.amazon.com/bedrock/home?region=<region>#/model-quotas

Bedrock 控制台自带的配额页面，把与模型推理相关的配额按模型整理出来，比 Service Quotas 的平铺列表直观。

页面上能看到什么

  • 按模型分组的推理配额：RPM、TPM（部分分 Input / Output，部分是合并 TPM）
  • 每条配额的当前生效值
  • 部分新模型显示 TBD —— 动态配额，详见标签页 ④
  • 提额 / 申请入口

和 Service Quotas 的分工

场景建议用
"Claude XX 在这个区域每分钟能跑多少"Model quotas（按模型直接找）
"这个模型显示 TBD，限额到底多少"Model quotas + 标签页 ④
"查批量推理 / 微调 / Agents 的限额"Service Quotas
"对比默认值，审计哪些配额被改过"Service Quotas（有两列对比）
两个页面底层是同一套配额。Service Quotas 里能搜到明确数字的，以那个 Applied value 为准；只在 Model quotas 里显示 TBD 的，是动态配额。

burndown（token 折算率）

对合并计量的 TPM（不分输入/输出），输出 token 消耗配额更快——部分较新的 Anthropic 模型按 1 个输出 token ≈ 5 个输入 token 折算。所以输出重的负载"看着有余量"也可能被限流。具体折算率以 AWS 官方文档为准。像 mantle 端点那样拆成 Input TPM / Output TPM 两条的，各算各的，不涉及折算。

配额值显示 "TBD" 是什么意思？

TBD = To Be Determined（待定）。表示这条配额是动态配额：AWS 不公布固定数值，由 Bedrock 根据区域容量、账号历史用量等因素动态分配。常见于较新发布的模型。

TBD 意味着什么

方面说明
有没有上限？有，只是不公开。打满同样返回 429 / ThrottlingException
Service Quotas 里能看到吗？通常搜不到具体数值——所以要去 Model quotas 页面看
能自助提额吗？一般不能走标准提额流程。会随稳定用量自动增长；大容量需求走工单 / 联系客户团队
值是固定的吗？不是。同一账号不同时间、不同区域拿到的额度可能不同

为什么这样设计

  • 新模型上线初期区域 GPU 容量有限且波动大，固定配额要么太保守要么兑现不了
  • 按"实际在用的账号"倾斜容量，防止配额被囤积
  • 模型成熟后，部分配额会从 TBD 转为公布的固定值

TBD 模型被限流怎么办

  1. 指数退避重试：SDK 一般自带，确认没关掉
  2. 削峰：排队、限速器、错峰任务
  3. Prompt caching：命中缓存的输入 token 大幅降低配额压力
  4. 换路径 / 换区域：跨区域 profile 就是为了借多区域容量
  5. 非实时任务走批量推理（Batch inference），配额分开计
  6. Provisioned Throughput：买断专用吞吐（成本高，适合稳定大流量）
  7. 持续稳定地用：动态配额通常随健康用量自动上调
  8. 都不够 → 开工单 / 联系客户团队，带上用量数据和业务场景
别人报告的"某模型 RPM/TPM 数字"不代表你账号的额度——动态配额因账号而异，以自己账号实测为准。

429 / ThrottlingException 排查流程

程序报 429 / ThrottlingException │ ▼ ① 确认调用路径：代码用的是哪个端点/模型 ID？ ├─ anthropic.claude-* → 直连按需配额 ├─ us.anthropic.claude-* → Cross-region 配额 └─ AnthropicBedrockMantle → [bedrock-mantle endpoint] 配额 │ ▼ ② 到对应配额页找那一行，看 Applied value ├─ 有固定值 → 对比自己的实际吞吐（RPM？Input TPM？Output TPM？） ├─ Applied 远低于 Default → 账号被动态降额（见标签页 ⑦） └─ TBD → 动态配额，见标签页 ④ │ ▼ ③ 判断打满的是哪个维度 "Too many requests" → RPM "Too many tokens" → TPM（先怀疑 Output TPM / burndown 折算） │ ▼ ④ Applied 明明够却间歇性 429？ → 区域容量拥挤（按需配额是上限不是保证） → 错峰 / 换区域 / 走跨区域 profile │ ▼ ⑤ 对策：提额（可调的）/ 缓存 / 削峰 / 批量 / 换路径

怎么知道自己实际用了多少

  • CloudWatch：Bedrock 命名空间下有调用数、token 数、InvocationThrottles（被限流次数）等指标，可按模型 ID 维度做告警
  • 应用层自统计：每个响应的 usage 字段有 input/output token 数，按分钟窗口累计后和 Applied 值对比
  • 配额页面的 Utilization 列大多是 Not available，别指望它

提额申请的实用建议

  • 先算清楚要多少：峰值并发 × 平均每请求 token 数 × 每分钟请求数，留 30–50% 余量
  • 输出 TPM 和输入 TPM 分开申请（拆分计量的），瓶颈通常在输出侧
  • 提额是按区域的，多区域部署要分别申请
  • 审批需要时间（自动批几分钟，人工审可能几天），上线前提前办
  • 大幅提额附上业务场景和用量预估，通过率更高

Kiro 的 429 由什么决定

Kiro 的 429 和你的 AWS 账号 Bedrock 配额无关。Kiro 是 AWS 托管服务，推理跑在 AWS 自己的容量池上，不消耗你账号的 Bedrock 配额。Service Quotas 提额对 Kiro 无效，且 AWS 不公布 Kiro 的精确限流阈值。

四层决定因素

因素说明
1. 短窗口频率限制
（最常见）		 服务端按账号的短窗口吞吐限制（类似 RPM），和月度 credits 独立——credits 没用完照样 429。关键坑：一个 prompt ≠ 一次后端调用，agent 执行任务（spec、hooks、多步循环）会在后台发大量模型调用，"才发一句话就 429" 是正常现象
2. 风控/信任状态
（最隐蔽）		 报错带 "Due to suspicious activity..." 的是风控限流。触发因素：VPN/代理接入、共享 IP、异常使用模式。有用户反馈解封后仍处于"隐藏的降级信任状态"被持续严格限流。国内经代理使用命中率高
3. 订阅层级与 credits 套餐决定月度额度（Free 50 / Pro $20 1,000 / Pro+ $40 2,000 / Power $200 10,000 credits，按 prompt 复杂度分数计扣）。credits 耗尽和 429 是两种不同拦截：前者提示额度用完，后者是 "Too many requests"
4. 上游容量（高峰拥挤） 共享容量池，美区工作时间高峰更容易限流；模型越高端容量越紧张。无法控制，只能重试/错峰

对症下药

症状对策
偶发 429，重试就好短窗口限流 → 等 30s~几分钟，避免连续快速触发大任务
提示 suspicious activity风控 → 停用 VPN/代理、换干净网络；持续则去 GitHub issues 提工单
一直 429、几乎不可用可能是隐藏信任降级或服务端事件 → 查 status、提 issue
大任务频繁中断把 spec 拆小、减少一次交互触发的 agent 步数、精简上下文

和 Bedrock 的本质区别

Bedrock 的 429：能查到具体配额数字、能自助提额。
Kiro 的 429：阈值不公开、不可自助调整，能动的杠杆只有套餐、使用节奏和网络环境。

"256V 账号" ≠ 高 Bedrock 配额

256v（EC2 vCPU 配额 256）和 Bedrock 的 RPM/TPM 没有任何直接关系。AWS 各服务的配额相互独立——256v 衡量的是 EC2 的 vCPU 上限，社区拿它当"账号成熟度"的代理指标，但一个 256v 账号的 Bedrock applied 配额照样可能很低。

你的真实 RPM/TPM 由什么决定

Bedrock 配额 = 账号 × 区域 × 模型 × 调用路径 四个维度共同决定，而且：

  1. AWS 按账号动态下调。"AWS default" 只是纸面值，新账号 / 低消费史 / 低信任账号的 applied 值经常远低于 default（社区大量案例：默认 50 RPM 的模型，新账号 applied 只有 1~2 RPM）。这是"高配账号也一调就 429"的主因
  2. 新模型是 TBD 动态配额，连固定数字都没有，随容量和用量历史浮动
  3. 即使配额没打满也可能 429：按需调用的配额是"上限"不是"保证"，区域容量紧张时照样限流

查自己账号真实数字的 CLI（换成实际 region）

你账号实际生效的值（关键看这个）：

aws service-quotas list-service-quotas ` --service-code bedrock --region us-west-2 ` --query "Quotas[?contains(QuotaName,'Claude')].{Name:QuotaName,Applied:Value}" ` --output table

AWS 纸面默认值（对比用）：

aws service-quotas list-aws-default-service-quotas ` --service-code bedrock --region us-west-2 ` --query "Quotas[?contains(QuotaName,'Claude')].{Name:QuotaName,Default:Value}" ` --output table
两条结果对比：Applied ≠ Default 的行就是被改过的配额（提额过或被降额/清零）。Applied 远小于 Default → 账号被动态降额，这基本就是你 429 的答案。TBD 动态配额不会出现在 CLI 结果里，要看 Bedrock 控制台的 Model quotas 页面。

被降额了怎么办

  • 正常持续使用：健康的用量历史会让动态配额缓慢恢复/增长
  • 有付费历史 + 开 support 工单说明业务场景，可申请提额（新账号通过率低）
  • 代码侧兜底：指数退避重试（SDK 默认开着别关）、错峰、prompt caching、多区域 fallback
  • 非实时任务走批量推理，稳定大流量考虑 Provisioned Throughput
如果账号是买来的：这类账号常见"看着 EC2 配额高、Bedrock 早被风控降额"的情况，且提额申请很难通过。买前无法验证 Bedrock applied 值，买后先跑上面的 CLI 摸底。
